**📌 TIL: iOS RunLoop의 역할과 비동기 시스템과의 차이 이해하기**

## 🛠 탐구 계기

iOS 앱 개발 과정에서 Timer, URLSession, 사용자 입력 이벤트 등은 자연스럽게 사용해왔지만,</br>
이들이 내부적으로 어떻게 동작하는지에 대해서는 깊이 고민해본 적이 없었습니다.

RunLoop에 대해 공부를 진행하면서 다음과 같은 질문들이 혼재되어 혼란을 느꼈습니다.

- 타이머는 내가 직접 생성하는데 왜 외부 이벤트처럼 RunLoop가 필요한가?
- URLSession 응답 대기는 RunLoop가 아닌가?
- 비동기 작업과 이벤트 감지는 무엇이 다른가?
- 왜 백그라운드 스레드에서는 Timer가 동작하지 않는가?

이러한 질문을 해결하기 위해 RunLoop의 역할과 비동기 시스템과의 차이를 중심으로 이론을 정리해보았습니다.

---

## ✅ 내용 정리

### RunLoop란 무엇인가

Apple 공식 문서에 따르면 RunLoop는 다음과 같이 정의됩니다.

> RunLoop 객체는 소켓, 파일, 키보드, 마우스 등의 입력 소스와 타이머 이벤트를 수신하고 처리하는 이벤트 처리 루프입니다.</br>
> 스레드가 할 일이 있을 때는 실행하고, 없을 때는 대기하도록 하기 위한 스레드 관리 메커니즘입니다.

즉 RunLoop는 스레드가 불필요하게 CPU를 점유하지 않도록 하면서, 외부에서 발생하는 이벤트를 감지하고 처리하기 위한 이벤트 루프입니다.

#### RunLoop가 처리하는 이벤트의 종류

RunLoop가 감지하는 이벤트는 크게 두 가지로 나뉩니다.

1. Input Source
   - 다른 스레드나 시스템으로부터 전달되는 비동기 이벤트
   - 예: 사용자 입력, 포트 메시지, 커스텀 이벤트
2. Timer
   - 특정 시점이나 주기에 맞춰 실행되는 예약 기반 이벤트
   - 예: Timer, CADisplayLink

#### RunLoop의 기본 특징

- 각 스레드는 자신만의 RunLoop를 가질 수 있습니다.
- RunLoop는 스레드 생성 시 자동으로 실행되지 않으며, RunLoop.current로 가져와야 합니다.
- 생성되었다고 해서 자동으로 실행되지 않고, run() 계열 메서드를 호출해야 동작합니다.
- RunLoop는 이벤트가 없을 경우 sleep 상태로 대기하며, 이벤트가 발생하면 깨어나 처리합니다.
- Main Thread의 RunLoop는 시스템에 의해 자동 생성 및 자동 실행됩니다.
- RunLoop는 기본적으로 한 사이클 단위로 이벤트를 처리합니다.

#### RunLoop의 내부 사이클 개념

RunLoop의 한 사이클은 다음과 같은 흐름으로 동작합니다.

1. 처리할 Input Source나 Timer가 있는지 확인
2. 이벤트가 있으면 처리
3. 처리할 이벤트가 없으면 sleep 상태로 진입
4. 새로운 이벤트가 도착하면 wake up 후 다시 처리

이 구조 덕분에 RunLoop는 이벤트가 없을 때는 자원을 낭비하지 않고, 필요할 때만 깨어나 동작할 수 있습니다.

### RunLoop 실행 방식

RunLoop는 상황에 따라 다양한 방식으로 실행할 수 있습니다.

run()

- RunLoop를 무한히 실행합니다.
- 스레드를 지속적으로 유지해야 할 때 사용합니다.
- 내부에서 명시적으로 중단하지 않는 한 종료되지 않습니다.

run(until:)

- 지정한 시점까지 RunLoop를 실행한 후 자동 종료합니다.
- 일정 시간 동안만 이벤트를 처리해야 할 때 사용합니다.

run(mode:before:)

- 특정 모드에서 한 번의 RunLoop 사이클만 실행합니다.
- 이벤트 처리 흐름을 세밀하게 제어해야 할 때 사용합니다.

#### RunLoop Mode의 의미

RunLoop는 실행 모드에 따라 처리할 이벤트를 구분합니다.

- .default: 일반적인 이벤트 처리
- .tracking: 스크롤, 터치 이동 등 UI 추적 중
- .common: 여러 모드에서 공통으로 동작해야 하는 이벤트

이를 통해 예를 들어 스크롤 중에는 특정 타이머만 멈추고,
다른 작업은 계속 수행하도록 제어할 수 있습니다.

### RunLoop는 언제 사용하는가

RunLoop를 직접 다뤄야 하는 대표적인 상황은 다음과 같습니다.

- 백그라운드 스레드에서 Timer를 사용해야 할 때
- InputStream, OutputStream 등 RunLoop 기반 API 사용 시
- 커스텀 스레드를 오래 유지해야 할 때
- RunLoop Mode를 기준으로 이벤트를 제어해야 할 때
- UI 테스트 등 이벤트 루프를 직접 제어해야 하는 경우

반대로 다음과 같은 경우에는 직접 RunLoop를 사용할 필요가 없습니다.

- GCD (DispatchQueue)
- URLSession 비동기 통신
- async/await, Task 기반 Swift Concurrency

⸻

### RunLoop와 비동기 작업의 차이

RunLoop와 비동기 작업은 구조적으로 차이가 있습니다.

**RunLoop**

- 언제 이벤트가 발생할지 예측할 수 없음
- 외부 시스템에 의해 이벤트가 갑자기 발생
- 구조: 대기 → 이벤트 감지 → 처리

**비동기 작업**

- 개발자가 요청을 직접 발생시킴
- 응답을 기다리는 구조
- 구조: 요청 → 응답 대기 → 처리

이 차이로 인해 RunLoop는 “이벤트 감지 시스템”, </br>
비동기 작업은 “요청–응답 시스템”으로 이해할 수 있습니다.

#### Timer가 비동기가 아닌 RunLoop 기반인 이유

Timer는 생성 시 시스템에 작업을 위임하고,
개발자는 그 존재를 계속 추적하지 않습니다.

설정된 시간이 지나면 시스템이 “이제 실행할 시간이다”라는 신호를 보내고,</br>
이 신호를 감지해 실행하는 주체가 바로 RunLoop입니다.

> 즉 Timer는 비동기 작업처럼 응답을 기다리는 구조가 아니라,</br>
> 시스템 이벤트를 감지해 반응하는 이벤트 기반 모델이기 때문에 RunLoop가 필요합니다.

#### 왜 백그라운드 스레드에서는 Timer가 동작하지 않았는가

Main Thread는 RunLoop가 자동으로 실행되기 때문에
Timer 이벤트를 감지하고 처리할 수 있습니다.

반면 **백그라운드 스레드는 RunLoop가 자동으로 실행되지 않기 때문**에,
시스템에서 전달된 타이머 신호를 받아 처리할 수 없어 Timer가 동작하지 않았습니다.

-> 따라서 백그라운드에서 Timer를 사용하려면 RunLoop를 명시적으로 실행해주어야 합니다.

### 마무리 요약

- RunLoop는 이벤트 감지를 위한 스레드 관리 루프입니다.
- 비동기 작업과 RunLoop는 구조적으로 다른 개념입니다.
- Timer는 시스템 이벤트 기반이기 때문에 RunLoop에 의존합니다.
- Main Thread의 RunLoop는 UI 이벤트와 화면 갱신의 핵심입니다.
- 백그라운드 스레드에서는 RunLoop를 직접 실행해야 합니다.

⸻

## 📌 마무리

이번 RunLoop 정리를 통해 iOS에서 이벤트 처리가 왜 특정한 방식으로 동작하는지, </br>
그리고 Main Thread 중심의 구조가 어떤 설계적 의도를 가지고 있는지 구조적으로 이해할 수 있었습니다.

아직 비동기 스레드에서 RunLoop를 직접 생성하거나 제어해본 경험은 없지만,  
이번 학습을 통해 단순히 “동작한다 / 안 한다”의 문제가 아니라  
**이 작업이 이벤트를 지속적으로 감지해야 하는 구조인지**,  
혹은 **요청–응답으로 한 번 실행되면 끝나는 작업인지**를 먼저 구분하는 것이 중요하다는 기준을 세울 수 있었습니다.

앞으로 비동기 작업이나 타이머, 입력 이벤트를 설계할 때에는  
무조건 백그라운드 스레드를 사용하는 것이 아니라  
RunLoop가 필요한 상황인지, Main Thread에 맡겨야 하는 역할은 무엇인지 의식적으로 판단하며 설계할 계획입니다.
