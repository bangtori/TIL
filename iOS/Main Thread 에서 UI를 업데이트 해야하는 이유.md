**📌 TIL: Main Thread에서 UI 업데이트를 해야 하는 이유**

## 🛠 탐구 계기

iOS 개발을 하면서 “UI 업데이트는 반드시 Main Thread에서 해야 한다”는 규칙을 당연하게 받아들이고 사용해 왔습니다.

하지만 단순 암기가 아니라, 왜 그런 설계를 했는지, 그리고 Thread / Race Condition / RunLoop 관점에서 어떤 문제가 발생하는지를 명확히 이해하고 싶어 이론적으로 정리하게 되었습니다.

## ✅ 내용 정리

### Thread Safe란 무엇인가

Thread Safe란 멀티 스레드 환경에서 여러 스레드가 동시에 같은 자원에 접근하더라도 Race Condition(경쟁 상태)이 발생하지 않고, 항상 올바른 결과가 보장되는 상태를 의미합니다.

즉,

- 한 번에 하나의 스레드만 공유 자원에 접근하게 하거나
- 여러 스레드의 동시 접근을 허용하더라도 결과가 항상 동일하도록 보장하는 구조입니다.

#### Race Condition(경쟁 상태)

Race Condition이란 둘 이상의 스레드가 공유 자원(변수, 객체, 파일 등) 에 동시에 접근할 때, 실행 순서나 타이밍에 따라 결과가 달라지는 상태를 의미합니다.

<br>

예를 들어 balance = 1000 인 상황에서

> 스레드 A: balance = balance + 100</br>
> 스레드 B: balance = balance - 50

- 이 두 작업이 경쟁 상태에서 동시에 실행되면
  - 경쟁 상태에서는 두 스레드 모두 1000을 기준으로 계산하여 최종 값이 1100 또는 950 중 하나로 남게 됩니다.

- Thread Safe한 환경에서는
  - 어떤 스레드가 먼저 실행되든 이전 연산의 값을 참고하여 항상 최종 결과는 1050이 됩니다.

UI 객체 또한 내부적으로 여러 상태 값을 가지기 때문에,</br>
동일한 Race Condition 문제가 UI 레벨에서도 그대로 발생할 수 있습니다.

### UIKit은 왜 Thread Safe하지 않을까

UIKit은 기본적으로 Thread Safety를 보장하지 않는 프레임워크입니다.

> Thread Safe를 보장하려면 모든 속성과 메서드에 락(lock)과 동기화 처리가 필요하지만,
> UIKit처럼 규모가 매우 큰 프레임워크에서는 이는 심각한 성능 저하로 이어질 수 있습니다.

이러한 이유로 Apple은 성능을 우선시하여
UIKit을 non-atomic, 즉 동시 접근에 대한 보호 장치를 두지 않는 구조로 설계했습니다.

### 왜 UI 업데이트를 Main Thread에서 해야 할까

UIKit이 Thread Safe하지 않기 때문에,
여러 스레드에서 동시에 UI에 접근하면 Race Condition이 발생할 수 있습니다.

예를 들어,</br>

- 스레드 A: `view.removeFromSuperview()`
- 스레드 B: `view.backgroundColor = .red`

이 두 작업이 동시에 실행되면,</br>
이미 제거된 view에 접근하면서 예측 불가능한 에러가 발생할 수 있습니다.

이를 방지하기 위해 Apple은 UI 작업을 Main Thread 하나로 제한했습니다.</br>
Main Thread는 작업이 동기적·순차적으로 처리되기 때문에,</br>
UI 관련 Race Condition을 원천적으로 차단할 수 있습니다.</br>

즉, **Main Thread는 UIKit을 위한 자연스러운 임계 구역(Critical Section) 역할**을 하도록 설계된 것입니다.

### RunLoop 관점에서의 보완 이해

각 스레드는 RunLoop를 가질 수 있지만,</br>
자동으로 RunLoop 실행이 보장되는 것은 Main Thread뿐입니다.

Main Thread의 RunLoop는

- 사용자 터치 입력
- UI 이벤트 처리
- 화면 갱신

을 지속적으로 처리하도록 설계되어 있습니다.</br>

반면, 다른 스레드에서는 RunLoop가 자동 실행되지 않으며 개발자가 직접 실행과 반복 구조를 관리해야 합니다.

이러한 구조적 특성 때문에 UI 이벤트 처리와 화면 갱신은 Main Thread의 RunLoop를 중심으로 동작하도록 설계되었고,</br>
UI 작업을 Main Thread에서 수행하도록 강제하는 것이 가장 안전한 선택이 되었습니다.

### 마무리 요약

- UIKit은 성능을 위해 Thread Safety를 보장하지 않습니다.
- 멀티 스레드에서 UI를 건드리면 Race Condition이 발생할 수 있습니다.
- Main Thread는 UI 작업을 순차적으로 처리하는 임계 구역 역할을 합니다.
- Main Thread의 RunLoop는 자동 실행되며 UI 이벤트 처리에 최적화되어 있습니다.

클린 아키텍처를 비롯한 여러 아키텍처 패턴들이 UI 레이어와 도메인·데이터 레이어를 분리하는 이유가 단순한 역할 분리가 아니라 Thread Safety와 실행 책임을 명확히 하기 위한 설계 선택일 수 있다고 생각하게 되었습니다.

앞으로 아키텍처를 설계할 때에는
